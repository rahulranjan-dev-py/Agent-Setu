# Bug, risk and security review: 28-09-2026 (app 1.1.3 → fixes in 1.1.4)

Scope: the whole app as released in 1.1.3 (code, manifest, CI workflows, docs), reviewed against the
guardrails in `CLAUDE.md` and the promises in `docs/PRIVACY.md`. Method: three independent read-only
passes (security; crash and logic bugs; privacy, data retention and supply chain), every finding
re-checked against the code before it was fixed. Nothing was tested on a phone from this sandbox: the
fixes compile and the unit tests pass on GitHub Actions; the on-phone checks to do are listed at the end.

Threat model: an offline app on the user's own phone. Attackers considered: someone holding the
unlocked phone, a crafted backup file, and whoever controls the GitHub repository or account.

## 1. Summary

| Area | High | Medium | Low | Info | Fixed in 1.1.4 | Needs the owner |
|---|---|---|---|---|---|---|
| Security | 0 | 2 | 6 | 5 | all High/Medium/Low | environment-protected release secrets, tag ruleset |
| Bugs | 2 | 7 | 13 | – | 2 High, 7 Medium, 11 Low | – |
| Privacy and CI | 0 | 6 | 6 | 6 | 11 | tag ruleset, Gradle checksum |

No finding allowed customer data to leave the phone, and none broke the guardrails on Aadhaar, PAN,
bank numbers, departmental systems or tracking. The two highest-impact items were a data-loss bug in
the ledger (Undo then Collected recorded nothing) and the in-app updater trusting `version.json`
alone for what to install.

## 2. Security findings

| # | Sev | Where | Finding | Fix (1.1.4) |
|---|---|---|---|---|
| S1 | Medium | `UpdateInstaller`, `UpdateCheck` | The downloaded APK was verified only against the checksum in `version.json`, which comes from the same place as the link. Whoever controls `main` could point the app at any `.apk`, and the "Install" dialog would present it as an Agent Setu update. Android would still refuse a same-package APK with another key, but a different package installs as a new app; for `.debug` builds the signing key is public. | `apkUrl` must start with the app's own release address (`BuildConfig.APK_URL_PREFIX`); after the checksum, `ApkCheck` opens the file and requires the same package name, the announced `versionCode` and the same signing certificate as the running copy. Otherwise the file is deleted and "not a genuine release" is shown. |
| S2 | Medium (availability) | `DatabaseKeyProvider` | If the Keystore key was lost (system repair, data copied by a vendor tool) while the wrapped passphrase remained, the provider silently made a new key, decryption failed inside Hilt, and the app crashed on every launch with no way to reach "Delete all data". | A missing key or a malformed stored value now raises `DatabaseKeyUnavailableException`; `MainActivity` checks `isUsable()` before the app starts and shows `DataUnavailableScreen` (explanation + "Erase and start again"). The Keystore key is generated only on first run. |
| S3 | Low | `AppLock` | The wait after wrong PINs compared wall-clock times; moving the phone's date forward skipped it. | The wait is also recorded on the monotonic clock with the boot count; the longer of the two applies. |
| S4 | Low | `AppLock`, `LockScreens` | If the process died between saving the PIN and confirming the recovery code, the PIN existed with a code nobody had seen; a rotation also lost the code dialog. | "PIN step done" is stored only when the code is confirmed (so setup returns after a crash); the code survives rotation. |
| S5 | Low | `UpdateInstaller` | Two quick taps on Download could run two downloads into one file; cancel during verification raced with completion; HTTP 416 was trusted as "complete". | State is claimed synchronously before launching; cancellation is honoured before and after verification; 416 deletes the stale partial and restarts once. |
| S6 | Low | `BackupCrypto`, `BackupScreen` | No size caps: a crafted backup could exhaust memory; a hostile iteration count (up to 10 million) was honoured before authentication; 150,000 PBKDF2 rounds is below current guidance. | File capped at 64 MB before decrypting, decompressed payload at 256 MB; accepted iterations 10,000–1,000,000; new files use 600,000 rounds (older files still open). Unit test added. |
| S7 | Low | `MainActivity` | Customer data, the full policy number, the PIN and the one-time recovery code could appear in screenshots and the Recents thumbnail. | `FLAG_SECURE` on the lock and PIN-setup screens; Recents thumbnail disabled on Android 13+. Ordinary screens stay capturable on purpose so testers can send screenshots (owner may tighten later). |
| S8 | Info | strings | "official group" / "official link" wording, which the guardrails ask to avoid. | Reworded to "Agent Setu users group" in both languages. |

Verified as sound (no change): SQLCipher passphrase generation and Keystore wrapping; backup file
format (random salt and IV, authenticated header, GCM); PIN and recovery-code hashing (PBKDF2,
constant-time compare, shared lock-out that survives restarts); lock state machine; biometric prompt
configuration; manifest (three permissions, nothing exported beyond the launcher, `allowBackup`
off, extraction rules); notification privacy; error-report masking; the only network calls are the
two update requests, both HTTPS GET with nothing sent.

## 3. Bugs

| # | Sev | Where | Finding | Fix (1.1.4) |
|---|---|---|---|---|
| B1 | High | `ReminderRepository`, `CommissionRepository` | Collected → Undo → Collected recorded nothing: Undo soft-deleted the ledger entry, the second Collected found the deleted row and returned it unchanged. The premium looked handled but earned nothing. | A soft-deleted entry is revived under its own id with recomputed values; Undo treats it as newly created again. |
| B2 | High | `ReminderRepository.markCollected` | Collecting a premium whose reminder was dated before an edited start date hit a `require` in `PolicyDates.policyYear` and crashed the app. | Such a reminder counts as the first policy year; Today's actions are wrapped so a failure never closes the app. |
| B3 | Medium | `ReminderWorker.reschedule` | `ExistingPeriodicWorkPolicy.UPDATE` keeps the original period start, so a new reminder time took effect late or not at all. | `CANCEL_AND_REENQUEUE`. |
| B4 | Medium | `AddBusinessScreen` edit path | Editing dates, frequency or product left the old reminders on Today (regeneration only adds). | `ReminderRepository.holdingEdited` removes the holding's open reminders and plans them afresh. |
| B5 | Medium | `ReminderRepository.followUpDone` / `undo` | Undo of a follow-up restored the lead but left the reminder created for the new date. | The created reminder id travels in the undo action and is removed on undo. |
| B6 | Medium | `HomeViewModel` | `today` was captured once; after midnight the sections, the month card and the horizon were a day off until the view model was recreated. | Today is re-read on every resume (`LifecycleEventEffect`); sections and month totals follow it; reminders regenerate on a date change; the backup nudge and notification card refresh too. |
| B7 | Medium | `SeedLoader`, `CommissionRepository.changeRate`, `InterestRateRepository` | A revised sample rule kept `isSample = true` on its closed row; a later seed update would have revived it, making every new entry ambiguous ("No rule"). | The closed row is marked as the user's own (`isSample = false`). |
| B8 | Medium | `RuleMatcher`, `RuleEditScreen` | A user rule of the same shape as a sample tied with it (result: "No rule"), and there was no way to end or remove a rule. | A user-defined rule wins a tie against a sample (two user rules still clash); "End this rule" from a date in the rule editor. |
| B9 | Medium | `CommissionRepository` | Entries recorded as "No rule" stayed that way after the user added the missing rule. | `recomputeNoRuleEntries` runs after adding or changing a rule. |
| B10 | Low | `Migrations` | `abs(random())` in the 2→3 backfill can overflow for one value in 2^64. | `(random() & 3)`. |
| B11 | Low | `AddBusinessScreen` | Switching to a custom product kept the previous product's suggested maturity; maturity before start was accepted; a missing product row made Save do nothing; a pre-1.1.1 policy's last-4 was silently stored as its "full number" on the next save. | Suggestion cleared; maturity must not precede start; customer id set first; last-4 kept as is unless a full number is typed (with a hint). |
| B12 | Low | `RuleAddScreen` | Term band with min above max was accepted (a rule that never matches). | Refused with an error. |
| B13 | Low | `BackupManager` | A hand-edited backup with a non-numeric rate would crash every rates screen after restore. | Restore refuses such a file. |
| B14 | Low | `CustomerDao.search` | `%` and `_` in the search box acted as wildcards. | Escaped. |
| B15 | Low | `CommissionScreen` | An amount of 0 was rejected silently. | Error shown; statements need a positive amount too. |
| B16 | Low | `HomeScreen` | The notification-permission card did not refresh after returning from Settings. | Re-checked on resume. |

Not changed (noted for later): follow-up reminders of leads marked issued/lost would still show, but
no screen changes lead stages yet; a permanently denied notification permission has no "open
settings" shortcut.

Verified as fine: `refNumber` is read and written only on the policy's own screen; notifications,
share cards, error reports and backup file names carry no policy numbers; app data is excluded from
Android backup and device transfer; CI never prints secrets, never signs pull requests, and removes
the keystore after each run; the only key ever committed is the public debug key.

## 5. For the owner (cannot be done from the code)

1. **GitHub → Settings → Environments:** create `release`, move the four `RELEASE_*` secrets into it
   with yourself as required reviewer, and reference it from `release.yml` (`environment: release`).
   Then a leaked token or a stray `v*` tag cannot produce a signed release without your approval.
2. **Rulesets:** protect `main` (no force-push, PRs only) and tags matching `v*` (creation by you only).
3. **Gradle wrapper:** add `distributionSha256Sum` for 8.14.3 to `gradle/wrapper/gradle-wrapper.properties`
   (the checksum server was unreachable from the review sandbox).
4. **On-phone checks for 1.1.4:** set a PIN and rotate the phone while the recovery code shows; try
   five wrong PINs, move the date forward, confirm the wait remains; delete a customer and restore a
   backup taken afterwards, confirming no policy number comes back; edit a policy's start date and
   collect the next premium; tap Download on the 1.1.5 update when it exists and confirm the
   "genuine" check passes.
